## 残す情報

**軸の名前・クォータ日・件数の 3 つだけです。** 利用者の識別子を持ちません。渡す入口もありません。

**作成時刻・更新時刻を持ちません（`t.timestamps` を置きません）。** 作成時刻は「その日にはじめて起きた瞬間」をマイクロ秒で残します。`quota_consumptions`（利用者の識別子を持ちます）・`prompt_requests`・記録のいずれとも時刻で突き合わせられますので、**「その日の最初に上限へ達したのがどなたか」が絞り込めます。** 件数の少ない日ほど絞り込めます（PR #164 のレビューで指摘されました）。**集計に必要なのは日と件数だけです。**

**件数の列名を `occurrences` にします。** `count` だと `MetricEvent.count`（行数）と紛れ、集計の画面で静かに行数が返ります。

## 判断したこと

**測定は本業の脇にあるものです。本業の失敗の種類を書き換えません。** `Metrics::SideChannel` を通します。

**受け止める範囲は、守りたいことから決めます。** 守りたいのは「上限到達のお知らせが失われないこと」と「やり直せない状態を残さないこと」です。**記録の置き場が落ちる形は 1 つではありません。** `upsert` は書き込みを組み立てる前に列と一意索引を調べますので、表がまだ無ければ `ArgumentError`、列の名前がずれていれば `ActiveModel::UnknownAttributeError` になります。**どちらも `ActiveRecord::ActiveRecordError` ではありません**（2 回目のレビューで実測されました）。**種別で数え上げると必ず漏れますので、受け止めないものだけを名指しします。**

**握りつぶしません。** 失敗そのものを **`warn`** で残します。`Trace.step` は成功すると「完了」と書きますので、**失敗の記録が「完了」の行として埋もれます。気づけない記録は、握りつぶしと区別がつきません。**

**定義に無い軸は受け止めません。** それは書き間違いであり、失敗させるべきものです。

**数え上げを、データベースの側で 1 文で行います。** 読んでから足して書くと、同時に呼ばれたときに数が合いません。行に錠をかける形は、呼び出す側が例外の処理の途中にあるときに入れ子のトランザクションが中断状態になり、記録そのものが落ちました。

**検証を通しません（`upsert`）。** 軸の名前は先に検め、日と軸の重なりは一意索引が止めます。

## 既知の制限（申し送り）

**呼び出す側がトランザクションで包むと、上限到達の記録が巻き戻ります。** `Metrics::Recorder` は自前のトランザクションを持ちません。**枠を取る処理の中で見れば巻き戻りませんが、外側で包まれると巻き込まれます。**

**巻き戻るのは、記録だけではありません。** 記録の書き込みが SQL の段で失敗すると、**その時点で呼び出す側のトランザクションが中断状態になります。** `Metrics::SideChannel` はその失敗を受け止めますので、**呼び出す側は「成功した」と受け取ります。** ところが、そのあとの問い合わせがすべて拒まれ、**本業の変更まで巻き戻ります**（2 回目のレビューで実測されました）。

    settle! の戻り = refunded（呼び出す側は成功と受け取ります）
    最終の枠       = reserved（返還が巻き戻っています）

**この食い違いは静かです。** だからこそ、包んで呼ばないでください。**この振る舞いも、既知の制限としてテストで固定しています。**

**`Quota::Reservation.reserve!` ・ `settle!` を、トランザクションで包んで呼ばないでください。** 実装のコメントにも書きました。**この制限を固定するテストを置いています**ので、直したときに赤くなり、申し送りを消し忘れずに済みます。

生成リクエスト API（issue #55）は、この申し送りに従って**包まずに**呼びます。
