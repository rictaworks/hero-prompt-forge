### 要修正 1：`required` の文言が無いため、利用者を欠いた保存が別の例外になります

- 該当箇所：`src/backend/config/locales/ja.yml:8-15`、`src/backend/app/models/quota_consumption.rb:32`
- 観点：DP（Fail Fast・想定外を分かる形で失敗させること）、QC10（エラーハンドリング）

`belongs_to :user`（`:32`）が失敗したときの文言 `activerecord.errors.messages.required` が `ja.yml` にありません。`config/application.rb:38` で未定義の文言を例外にしているため、次のとおり例外の種類が変わります。手元で確認した結果です。

| 呼び出し | 起きる例外 |
|---|---|
| `QuotaConsumption.create!(quota_day: ...)`（利用者なし） | `I18n::MissingTranslationData` |
| `QuotaConsumption.create!(user: ..., quota_day: nil)` | `ActiveRecord::RecordInvalid` |
| `QuotaConsumption.create!(..., status: 'x')` | `ActiveRecord::RecordInvalid` |
| 同じ日に 2 件目を `create!` | `ActiveRecord::RecordInvalid` |

利用者を欠いた保存だけ、検証の失敗ではなく文言の欠落として失敗します。原因の切り分けが遠回りになり、`record_invalid`（`ja.yml:13`）を足した意図（保存の失敗を読める形で知らせること）も、この経路では効きません。`ja.yml` へ `required` を 1 行足せば揃います。

なお `spec/models/quota_consumption_spec.rb:31-33` の「利用者が無ければ保存できません」は `valid?` を見るため文言を組み立てず、この差に気づけません。`create!` を使う例を 1 つ足すと固定できます。

この欠落は既存からの持ち越しでもあります（この PR より前は `activerecord` の文言が 1 つもありませんでした）。`format`（`user.rb:16`）・`length`（`project.rb:21` 等）・`numericality`（`prompt_output.rb:17-19`）の文言も未定義で、同じ形で失敗します。**受け入れ条件の範囲外ですので、この PR での対応は `required` の 1 行に留め、残りは「使っている検証の文言がすべて揃っていることを確かめるテスト」とあわせて別 Issue にすることをご提案します。**

### 提案 1：状態遷移の実装が `PromptRequest` と重複しています

`quota_consumption.rb:48-60` は `prompt_request.rb:51-63` とほぼ同じ内容です（例外の型と定数の参照先だけが違います）。3 つ目が出る前に、`TRANSITIONS` を参照する共通の concern（例：`app/models/concerns/status_transitions.rb`）へまとめる余地があります。DP は重複を避けるとしつつ「無理な共通化はしない」とも定めており、いまは 2 か所ですので今回の修正は不要と考えます。issue #37 で 3 か所目が出た時点でのご検討をご提案します。

### 提案 2：使い先の無い scope が 2 つあります

`quota_consumption.rb:40`（`for_day`）と `:41`（`outstanding`）は、実装にもテストにも呼び出し側がありません。YAGNI の観点では、使う場所が決まる issue #37 で、使い方に合わせて足す形が確実です。あわせて `:41` の `'reserved'` は `STATUSES` と別に書かれた素の文字列ですので、定数を経由すると状態名の変更に強くなります。

### 提案 3：`reset_by_admin` だけでは issue #67 の受け入れ条件を満たせません

migration `:16` の `reset_by_admin` は真偽値です。issue #67 の受け入れ条件は「実施者・日時が記録されます」ですので、そのままでは実施者と日時を残せません。`requirements.md` 4.4 も「リセットは実施者・日時とともに記録する」としています。issue #36 の受け入れ条件には含まれませんので今回の修正は不要ですが、issue #67 で列を足す migration が要る点を、あらかじめ Issue へ書き添えておくことをご提案します。

### 提案 4：状態の列にデータベース側の制約がありません

`status` は検証（`quota_consumption.rb:37`）だけで守られており、生の SQL では定義に無い値を書き込めます（手元で `bogus` を書き込めることを確認しました）。件数の担保をデータベースに置いた考え方に揃えるなら、状態にも CHECK 制約を置く選択があります。既存の `prompt_requests` も同じ作りですので、この PR だけで直す点ではありません。表全体の方針として別 Issue でのご検討をご提案します。
