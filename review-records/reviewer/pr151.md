## 要修正

### 要修正 1. 冠詞が誤った英文が、そのまま生成モデルへ渡ります

`src/backend/config/integration_rules.yml` 17 行目（`brand_color.accent`）です。

```
accent: "a %<color>s accent on a single object in the scene"
```

**色の名前が母音で始まる場合に `a orange` になります。** 実測です。

```
#F5A623 -> a orange accent on a single object in the scene
#D9C7A8 -> a orange accent on a single object in the scene
```

`config/color_names.yml` が持つ名前のうち `orange` が該当します。冠詞を語形から決めるか、冠詞を含まない言い回しへ改めてください。**`src/backend/spec/services/generation/conflict_resolver_spec.rb` に、組み上がった英文の妥当性を見る検査がありません。** 冠詞の検査を足してください。

### 要修正 2. 色の名前が、明度と彩度を捨てるため、実際のブランドカラーから離れます

`src/backend/app/services/generation/color_name.rb` 27 行目から 33 行目（`ColorName.of`）です。色相だけで名前を決め、明度と彩度は「色みが無いか」の判定にしか使いません。実測です。

| 色コード | 実際の色 | 付いた名前 |
|---|---|---|
| `#D9C7A8` | ベージュ | orange |
| `#0B3D2E` | 深緑 | teal |
| `#00704A` | 深い緑 | teal |
| `#001F5B` | 濃紺 | blue |
| `#5F7F7A` | くすんだ青緑 | teal |
| `#F5F5F5` | ごく淡い灰 | white |

**ベージュのブランドカラーが `a orange accent` になります。** アートディレクションとして、この指示を生成モデルへ渡すと、鮮やかなオレンジのアクセントが返ります。requirements.md 4.1 の 9 は、アートディレクションノートの確認観点に「**ブランドカラーの再現度**」を挙げています。色相だけの名前では、この観点を担保できません。

**一般的な英語の色名だけを使う方針は妥当です。** そのうえで、明度と彩度を修飾語で残してください（`deep green` ・ `pale orange` ・ `muted teal` ・ `navy` など）。いずれも一般的な英語であり、モデルによる解釈の割れは小さいと判断します。

### 要修正 3. `teal` を色名として出す設計が、製品の中核価値と衝突します

`src/backend/config/color_names.yml` 36 行目から 38 行目です。色相 150 度から 195 度に `teal` を割り当てています。

requirements.md 4.2 は、**クリシェ配色の代表として「紫〜ティールのグラデーション」を名指し**しています。規則辞書の初期値にも `purple to teal gradient` が入っています。**その語を、こちらから積極的にメインプロンプトへ入れる形になっています。** 無作為 16000 色を通したところ、**12.1 パーセント（1933 色）が `teal`** でした。緑寄りの色（`#00704A` ・ `#17CF73`）まで `teal` へ寄せている点も、範囲が広すぎます。

さらに、同じファイルの 9 行目から 10 行目のコメントは次のように書いています。

> **英語の一般的な色名だけを使います。**「ティール」「セルリアン」のような細かい名前は、モデルによって解釈が割れます。

**コメントが排したはずの名前を、データが採用しています。** どちらかへそろえてください。`teal` を残すのであれば、コメントを直したうえで、緑との境目（150 度から 170 度あたり）を緑側へ寄せてください。

### 要修正 4. 弱めて残したブランドカラーが、再び丸ごと消える経路が塞がれていません

`src/backend/app/services/generation/conflict_resolver.rb` 95 行目から 102 行目（`build_integration`）です。

弱めた素材は `a barely visible hint of teal` であり、**当たった語（`teal`）をそのまま含みます。** そのため、**この段のあとにアンチAIルック規則を当てると、弱めた素材ごと落ちます。** 実測です。規則辞書に `teal` を登録し、4.1 の 2→3→4→5 を通したあと、もう一度 `RuleEngine#apply` を当てました。

```
（統合の直後）
  12. a barely visible hint of teal

（そのあとに規則を再適用）
  ※ 12 が消えます
  notes:
    {:kind=>:brand_color_integrated, :color=>"#0E7C7B", :name=>"teal", :strength=>:weakened, :matched=>"teal"}
    {:kind=>:anti_ai_removed, :term=>"a barely visible hint of teal", :matched=>"teal"}
```

**ノートは `strength: :weakened` のまま残ります。** つまり、issue #51 のアートディレクションノートは「弱めて残しました」と説明しますが、**実際のプロンプトからは消えています。** 黙って消えるより悪く、**説明と実物が食い違います。**

`review-records/security-review/feature-issue-43-conflict-resolver.md` は「この段は、アンチAIルック規則より後に走ります。そのため、ここで足した素材が規則で落とされることはありません」と書いていますが、**この順序をコードで担保していません。** 組み立ての段（issue #146）は未実装で、順序は呼び出す側の作法に委ねられています。同じリポジトリの `CopySpace.reserved?`（`src/backend/app/services/generation/copy_space.rb` 71 行目から 84 行目）は、まさにこの危険のために「落ちた事実を見逃さない関所」を用意しています。**ブランドカラーにも同じ関所を置いてください。** 例として次のいずれかです。

- 統合済みの下書きへ `RuleEngine#apply` を当てたら失敗させます（`VersionMismatchError` と同じ考え方です）。
- `ConflictResolver.integrated?(draft)` を用意し、ノートが弱めたと記録している色の名前が `main_terms` に残っているかを確かめます。

### 要修正 5. 色の定義が人の編集で壊れても、黙って通る経路が残ります

`src/backend/app/services/generation/color_name_table.rb` 40 行目から 47 行目（`ensure_keys!`）です。**鍵の有無だけを見ており、値を見ていません。** 色相の範囲は `valid_range?` で形まで検めているのに、しきい値と `achromatic_name` は素通りします。実測です。

| 人の編集 | 起きること | 例外 |
|---|---|---|
| `achromatic_name: ''` | 灰色のブランドカラーが `a  accent on a single object in the scene` になります（色が消えます） | 出ません |
| `achromatic_name:`（値なし） | 同上 | 出ません |
| `achromatic_name: 灰色` | 日本語がプロンプトへ入ります | 出ません |
| `achromatic_saturation: 1.0` | **すべての色が `gray` になります** | 出ません |
| `black_lightness: 0.9` ・ `white_lightness: 0.1` | **すべての色が `black` になります** | 出ません |
| しきい値に文字列 | `ArgumentError: comparison of Float with String failed` | 出ますが、種類も場所も分かりません |

このクラスは冒頭に「**定義は人が編集するデータです。中身を信用しません。**」と書いています。**その約束に届いていません。** しきい値が 0.0 から 1.0 の数値であること、`black_lightness < white_lightness` であること、`achromatic_name` が色相の名前と同じ `/\A[a-z]+\z/` であることを検めてください。

## 提案

### 提案 1. 優先順位 ①コピースペース ＞ ②ブランドカラー が、出力に現れません

トーン装飾には `tone_restraint`（`the reserved copy area left plain`）を足しているのに、**ブランドカラーのアクセントには、余白の帯へ入り込まないための指定がありません。** 実測でも、コピースペース位置を左・右・下中央へ変えても、ブランドカラーの素材は一言一句同じです。`a teal accent on a single object in the scene` の「単一のオブジェクト」が余白側へ置かれると、**最上位の指定が二番目の指定に侵されます。** 「余白側ではない側に置く」旨を足すことを提案します。

### 提案 2. 優先順位 ②ブランドカラー ＞ ③スタイル系統 の解決がありません

矛盾解決はスタイル系統の素材へ一切触れません。実測です（抽象 + ブランド 1 色）。

```
- geometry derived from the brand mark
- implied motion along a single axis
- two brand colors plus one neutral        ← ③ スタイル系統
...
- a teal accent on a single object in the scene   ← ② ブランドカラー
```

**「2 色のブランドカラー＋中立色」（③）と「1 つのオブジェクトへのアクセント」（②）が同居します。** 前者は事実上の支配色の指定であり、この PR が掲げる「支配色にしません」と食い違います。指定は 1 色なのに「two brand colors」と言う点も食い違います。さらに、抽象の画に「object in the scene」はそぐいません。**4.1 の 5 は、まさにこの衝突で③を弱めよと定めています。**

### 提案 3. `the reserved copy area left plain` の `left` が、位置の「左」と読めます

`src/backend/config/integration_rules.yml` 41 行目です。同じプロンプトに `clear copy space across the right third of the frame` が入る場合、`left` が方向として読まれる危険があります。実測の出力でも `right third` と `left plain` が同居しました。`kept plain` ・ `rendered plain` など、方向と読めない語へ改めてください。あわせて、`config/copy_space_rules.yml` の `restraint`（`the ... third rendered as an even low contrast surface`）と役割が重複しています。

### 提案 4. 「英文ではありません」という例外文言に対し、実際は英文かどうかを見ていません

`src/backend/app/services/generation/integration_rules.rb` 79 行目から 85 行目（`ensure_text!`）です。空文字と空白だけを弾きます。実測では、`tones.trust` を日本語にしても、`brand_color.accent` を `%<color>s のアクセント` にしても通ります。打ち消しの言い回し（`no %<color>s anywhere`）も通ります。**テストは出来上がった素材について「日本語を作りません」「打ち消しを作りません」を確かめていますが、設定を人が編集した場合は素通りします。** 文言どおり非 ASCII と打ち消しを弾くか、例外の文言を実態へ合わせてください。

### 提案 5. 色空間の変換は、既製のライブラリで置き換えられます

`src/backend/app/services/generation/color_name.rb` 48 行目から 72 行目の RGB から HSL への変換は、教科書どおりの自作コードです。CLAUDE.md は「安全なライブラリ・OSS を使い、車輪の再発明を避け、オリジナルコードを少なく保ちます」と定めています。`color` などの枯れた gem で置き換え、**この製品固有の判断（範囲と名前）だけを設定ファイルに残す**ことを提案します。要修正 2 の修飾語を足す際も、既製の変換のほうが素直に書けます。

### 提案 6. 定義の読み直しの扱いが不揃いです

`ColorName` は `@definition` を記憶しますが、`ConflictResolver#initialize` は毎回 `IntegrationRules.load` を呼び、生成のたびに YAML を読みます。**PR 本文の「起動時に確かめます」は正確ではありません。** 実際には最初の組み立て時です。読み直しの方針をそろえ、本文の記載も実態へ合わせてください。

### 提案 7. 色の名前のテストの網羅が、本文の記載より狭いです

`src/backend/spec/services/generation/color_name_spec.rb` の `sample_colors` は、色相 60 度・180 度・300 度の 3 系統 48 色だけです。**PR 本文の「48 色を総当たり」は、色の全体を覆っていません。** 当方が無作為 16000 色を通したところ失敗は 0 件でしたので、**結論は正しい**のですが、テストは色相の全周を掃く形にしてください。要修正 3 の境目（緑と青緑、青緑と青）を固定する検査も足してください。

### 提案 8. 矛盾解決を二度当てても止まりません

`CopySpace` は `AlreadyReservedError` を持ちますが、`ConflictResolver#resolve` には同じ検めがありません。二度当てると、素材は `uniq` で重ならないものの、ノートだけが重複します。

## 申し送り

- **要修正 4 は、組み立ての段（issue #146）へ持ち越さないでください。** 順序を守らせる仕組みが無いまま組み立てを実装すると、この PR が塞いだはずの「黙って消える」経路が復活します。
- **要修正 2 の色名の粒度は、issue #51（アートディレクションノート）の「ブランドカラーの再現度」の実効性を左右します。** ノートで「この色はこう扱いました」と伝えても、渡した名前が実際の色と違えば、利用者は再現度を確かめられません。
- 提案 2 は、issue #43 の担当範囲を超える可能性があります。**スタイル系統の弱め方を別 Issue とするかどうかは、director の判断を仰いでください。** ただし、優先順位の 4 段のうち 2 段（③と④の関係、②と③の関係）が未着手であることは、issue を閉じる前に明記してください。

## 提案

1. **`green` の範囲が広すぎます。** 実測で全周の **27.8%**（70 度から 170 度）を占めます。1 回目に `teal` の 12.5% を指摘した基準を当てると、こちらのほうが広くなっています。実測では `#16A085`（青緑寄り）も `#556B2F`（オリーブ）も同じ `green` になります。`teal` の割合を 1 割未満に保つテストはありますが、**他の色名に上限のテストがありません。** 全色名に上限を掛けるテストを足すと、次に範囲を動かしたときの見落としを防げます。
2. **修飾語のしきい値の隙間です。** `#556B2F` は明度 0.302（`deep_lightness` 0.30 のすぐ上）・彩度 0.39（`muted_saturation` 0.30 のすぐ上）で、**修飾語が付かず `green` になります。** 暗く濁った色が、鮮やかな緑として生成モデルへ渡ります。3 つのしきい値のいずれにも掛からない「実際の色から遠い名前」が残る帯があることを、テストで押さえておくと安全です。
3. **`#FFC0CB` が `pale red` になります。** 一般的な英語では `pink` です。`pink` の帯（315-345 度）が実質マゼンタ寄りですので、赤の低彩度・高明度を `pink` へ寄せる余地があります。
4. **設定に `%` を書くと、生成時に例外になります。** `ensure_placeholder!`（`integration_rules.rb` 151-156 行）は `%<color>s` の有無だけを見ます。`"%<color>s with 100% coverage"` は検めを通り、`format` が `ArgumentError: unnumbered(1) mixed with named` を投げることを実測しました。**読み込み時に検めているのに、起動時ではなく生成時に落ちます。** `%<color>s` 以外の `%` を弾くか、読み込み時に一度 `format` を試すのが確実です。
5. **`DeepFreeze` を、既存の読み込みへも当ててください。** 新しい 2 つ（`ColorNameTable` ・ `IntegrationRules`）だけが入れ子まで凍り、`CopySpaceRules` ・ `WordForms` ・ `ProperNounRules` は器だけです。同じ道具が入った以上、扱いをそろえないと、どちらの作法が正なのか読めなくなります。
6. **ノートの `kind` を記号（Symbol）で比べています。** `ConflictResolver.integrated?` は `note[:kind] == TONE_NOTE_KIND` で判定します。いまは下書きが 1 リクエストの中で完結しますので問題ありません。**アートディレクションノート（issue #51）で下書きが保存・復元を挟むと、記号が文字列に変わり、関所が黙って効かなくなります。** その段で必ず確かめてください。

```
photoreal key_light（values_for）  = []
photoreal key_light（実際の素材）  = [..., "soft key light from a north-facing window", ...]
```

いまは `style_palette_conflict.items` が `palette` だけで、`palette` はどのスタイル系統でも入れ子の外にありますので、影響は出ません。**配色指定を入れ子へ移した瞬間に、弱めが黙って効かなくなります。**

### 取りこぼし B. 項目名が規則辞書側で変わると、黙って効かなくなります

`abstract` の `palette` を `color_palette` へ改名した規則辞書で実測しました。

```
出力 = ["geometry derived from the brand mark",
        "implied motion along a single axis",
        "two brand colors plus one neutral"]   ← 支配色の指定がそのまま残ります
ノート 0 件                                     ← 弱めなかった事実も残りません
```

`style_palette_conflict.items` は `config/integration_rules.yml`（Git 管理）にあり、スタイル仕様化規則は**管理画面から人が編集するデータ**（requirements.md 4.3）です。**別々に編集される 2 つを、名前の一致だけで結んでいます。** 一致しなくなっても、例外もノートも出ません。

**新しいスタイル系統を足すときに、配色指定へ別の名前（`color_scheme` など）を付けると、そこだけ弱めが効かない状態になります。**

`style_rules.rb` 76-82 行の注記は「定義されていない項目は、値を持たないものとして扱います。スタイル系統によって持つ項目が違うためです」と書いています。**系統ごとの有無を許すのは正しい判断です。** 一方、**どのスタイル系統にも無い項目名**は、系統ごとの違いではなく設定の誤りです。両者を分けて扱えば、正しい方だけを通せます。

対応の方向（いずれか 1 つで足ります）。

- `StyleRules#values_for` を `specification` と同じ探し方（入れ子を含む）にそろえます
- `StyleRules` の組み立て時に、`style_palette_conflict.items` の各項目が**少なくとも 1 つのスタイル系統に存在する**ことを確かめ、無ければ `InvalidDictionaryError` で止めます

**この 2 点は提案に留めます。** 初期の規則辞書では `illustration` ・ `abstract` の双方で正しく当たること、`配色指定を持たないスタイル系統では弱めません`（`conflict_resolver_spec.rb` 447 行）がその振る舞いを固定していることを、実測で確かめました。
