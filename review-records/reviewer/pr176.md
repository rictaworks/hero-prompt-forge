- **要修正 1：`config/llm.yml` の `endpoint` が効かなくなりました。**
  `src/backend/app/services/generation/gemini_client.rb` は、この PR で `settings.fetch('endpoint')` を使わなくなりました（`84cbe4a` 版の 73〜74 行にあった `endpoint` の組み立てが消えています）。実際の呼び出し先は `langchainrb` の中で決まります。**それでも `src/backend/app/services/generation/llm_settings.rb` の 17 行（`TEXT_KEYS`）と 42 行・73〜79 行（`ensure_endpoint!`）は `endpoint` を必須として検め続けます。**
  結果は 2 つです。**（1）設定を直しても呼び出し先は変わりません。** 別のホストへ書き換えても、テストは 1 件も落ちません（変異 M25）。**（2）「暗号化されていない呼び出し先を認めません」という検めが、実際の呼び出し先を守らなくなりました**（OWASP10 の A05、DP の「surprise の少ない構造」）。
  **`LangchainGemini` が `endpoint` を使うようにするか、`endpoint` を設定から外して記述をそろえるか、どちらかへ寄せてください。**

- **要修正 2：`langchainrb` の保守状況の書き方が、実態と合いません。**
  PR 本文と `review-records/security-review/feature-generation-pipeline.md` は、根拠として **「最終の push : 2026-08-26（前日）」「現役です」** を挙げています。**この事実は正しく、実測でも一致します**（`pushed_at` は `2026-08-26T15:18:50Z`、`archived` は false）。
  **しかし `src/backend/Gemfile` が留めているのは `~> 0.19.5` で、`Gemfile.lock` に入るのは 0.19.5 です。この版は 2025-05-01 の公開で、いまから約 16 か月前です**（RubyGems の版の一覧と GitHub の releases の両方で確認しました）。**動いている先端と、実際に入る版が別です。** 挙げた根拠は「実際に入る版の保守状況」を示していません（OWASP10 の A06、QC10 の QC09）。

  `src/backend/spec/jobs/reclaim_prompt_requests_job_spec.rb` の「重なった行を 1 回だけ投入します」は、`generating` の行を 1 件だけ作ります。**`unsettled_ids` は決着済み（`delivered` ・ `failed`）の行だけを拾いますので、この行は片方にしか入りません。重なりが起きていません。** `.uniq` を外しても緑のままです（変異 M7）。

- **要修正 5：投入し直しと定時の拾い直しが重なると、組み立てが 2 度走り、負けた側が理由の分からない失敗として残ります。**
  `src/backend/app/jobs/generate_prompt_job.rb` の `resumable?` は、`retrying?`（`executions > 1`）なら**行の持ち時間を見ずに真を返します。** 一方 `claimed?` は、置き去りの行を拾ったときに行を新しくします。**投入し直しの回は、その「新しくした」印を見ません。**

  **実際に再現しました。** 置き去りの行を定時の拾い直しが掴んで組み立てている最中に、投入し直しの回（`executions = 2`）を走らせたところ、**組み立てが 2 度走り、あとから収める側が次の失敗で落ちました。**

  ```
  ActiveRecord::RecordInvalid:
    Variation no はすでに使われています。のため保存できませんでした。
    ./app/services/prompt_requests/delivery.rb:61:in `store'
    ./app/jobs/generate_prompt_job.rb:135:in `perform'
  ```

  この失敗は `TRANSIENT_FAILURES` にも `PERMANENT_FAILURES` にも入りませんので、`rescue_from(StandardError)` が受けます。**そのとき行はすでに決着済みですので `record_failure` は何もせず、失敗だけが外へ出ます。** 利用者の記録は壊れません（案は 3 つのままです）が、**有償の呼び出しが二重にかかり、勝てなかった側が待ち行列に理由の分からない失敗として残ります。**

  **これは issue #169 が「拾い直しの穴」として挙げた症状そのものです。** 経路が違うだけです。届く道は次のとおりです。**投入し直しの 2 回目を走らせている最中に働き手が落ちる → 定時の拾い直しが 2 分後に新しい回を投入して組み立て始める → 待ち行列が 5 分後にもとの回（`executions = 2`）を戻す → その回は持ち時間を見ずに組み立てる。**

  **定時の拾い直しという 2 つ目の投入元が、この PR で初めて生まれました。** `retrying?` の素通りそのものは以前からありますが、**これまでは競う相手がいませんでしたので、届きませんでした。**

  **本 PR を止めるほどではないと判断します。** 拾い直しが無い状態（行が永久に `generating`、枠が `reserved` のまま、翌日以降も生成できない）のほうが重いためです。**ただし別 issue を必ず立ててください。** 投入し直しの回にも持ち時間を見せるか、収める側を冪等にするかの、どちらかが要ります。

### 提案

- **提案 1：定時の間隔（5 分）に、どのテストも当たりません。** 1 時間へ延ばしても緑のままです（変異 M5）。「置き去りと見なすまでの時間と釣り合わせます」という `config/recurring.yml` の意図が、後戻りしても気づけません。
- **提案 2：人物の構図の役割と、弱めた配色の役割に、どのテストも当たりません。** 前者を落とすと、実際の出力が **`The image shows the subject seen from behind.`** になります。**これは issue #156 が直そうとした形そのものです。** 後者は `src/backend/app/services/generation/style_palette.rb` の 28〜31 行のコメントが「引き継がないと既定の述語で述べられます」と書いている当の箇所です（変異 M14 ・ M19）。
- **提案 3：役割の対応が、黙って 1 件へまとまります。** `src/backend/app/services/generation/style_spec.rb` の 216 行は `decision[:compositions].index_with { PERSON_SAFETY_ROLE }.invert` です。**いまは構図が必ず 1 件（`compositions.first(1)`）ですので害は出ませんが、2 件以上になった日に、最後の 1 件だけが残ります。** `src/backend/app/services/generation/variation_notes.rb` の 65 行（`person_safety.first`）も同じ形です。**控えの `roles` が「役割 => 素材」の向きである限り、1 つの役割は 1 件しか持てません。** 素直な書き方へ改めるか、2 件以上を扱える形にしてください。
- **提案 4：`PERSON_SAFETY_ROLE` が 2 か所にあります。** `src/backend/app/services/generation/style_spec.rb` の 70 行と `variation_builder.rb` の 14 行が、同じ `'person_safety'` を別々に持ちます。片方だけを直せます。
- **提案 5：拾い直しに上限がありません。** 働き手が同じ場所で毎回強制終了する行（例：メモリ不足）は、`generating` のまま残り続けます。**5 分ごとに、際限なく投入され続けます。** 1 回ごとに有償の呼び出しがかかります。**回数の上限か、日をまたいだ行の打ち切りを、別 issue で足してください。**
