## 2. 指摘

### 2-1【要修正】記録の失敗が、上限到達のお知らせを覆い隠します

`src/backend/app/services/quota/reservation.rb` 39-42 行

```ruby
rescue ExhaustedError => e
  record_exhausted(now)
  raise e
end
```

`record_exhausted` が失敗すると、**`ExhaustedError` が呼び出す側へ届かず、記録の失敗がそのまま外へ出ます。**

実測しました（`Metrics::Recorder.record` がデータベースの失敗を投げる場合）。

```
呼び出し側が受け取る例外 = ActiveRecord::StatementInvalid: db down
```

`ExhaustedError` は `quota_day` と `reset_at` を持ち、お客さまへ「本日の枠を使い切っています。次は◯時に戻ります」とお伝えするための例外です。**測定のための記録がうまくいかなかっただけで、このお知らせが失われます。** 測定は本業の脇にあるものですので、本業の失敗の種類を書き換えてはならないと考えます。

DP（依存の向き・関心の分離）に反します。

**求めること**：記録の失敗が `ExhaustedError` を置き換えないようにしてください。握りつぶす形（フォールバック）は本プロジェクトが禁じていますので、**記録の失敗は失敗として残しつつ、呼び出す側へは `ExhaustedError` を届ける**形（例：記録を別の入口へ移す、`Trace` へ失敗を残したうえで元の例外を投げ直す）をご検討ください。**この振る舞いを固定する RSpec も添えてください。**

### 2-2【要修正】決着のあとで記録が失敗すると、やり直せない状態が残ります

`src/backend/app/services/quota/reservation.rb` 49-55 行

```ruby
consumption.transition_to!(next_status)
record_reclaimed(now) if next_status == 'refunded'
```

`transition_to!` が確定したあとに `record_reclaimed` が失敗すると、**枠は「返還済み」になっているのに `settle!` は失敗を返します。** 呼び出す側がやり直すと、予約中の記録がもう無いため `MissingReservationError` になります。

実測しました。

```
呼び出し側が受け取る例外 = ActiveRecord::StatementInvalid
枠の状態 = "refunded"
再実行の例外 = Quota::Reservation::MissingReservationError
```

QC10（異常時の一貫性）に反します。**やり直しの効かない中途半端な状態を残します。**

**求めること**：本業の決着と測定の記録の順序・境界を決めてください。少なくとも、**記録の失敗が決着の成否を書き換えない**ようにし、その振る舞いを RSpec で固定してください。

### 2-3【要修正】呼び出す側がトランザクションで包むと、上限到達の記録が巻き戻ります

PR 本文とセキュリティレビュー記録は「**上限到達は、枠を取る処理の外で記録します。巻き戻りません**」と書いています。**枠を取る処理の中で見れば、そのとおりです。** しかし `Metrics::Recorder#increment` は自前のトランザクションを持たないため、**呼び出す側がトランザクションで包んでいると、その巻き戻しに巻き込まれます。**

実測しました。

```ruby
ActiveRecord::Base.transaction { Quota::Reservation.reserve!(user: user, now: noon) }
# => ExhaustedError（外側のトランザクションが巻き戻る）
# 上限到達の件数 = 0
```

包まない場合は正しく 1 件になりますので、**現在のテストは緑のままです。** 生成リクエストの作成と予約をひとつのトランザクションで括るのは自然な書き方ですので、issue #55 で受け口を作るときに**静かに数が落ちます。**

いま `reserve!` ・ `settle!` を呼ぶ本番のコードがまだ無いため、**不具合として表に出ていません。** そのぶん、気づかないまま埋まる危険が高いと考えます。

**求めること**：次のいずれかをお願いします。

1. 呼び出す側のトランザクションに巻き込まれない形へ直し、**包んだ場合でも数が残ることを RSpec で固定する**
2. 直さない場合は、**「呼び出す側がトランザクションで包むと巻き戻ります」を実装のコメント・PR 本文・セキュリティレビュー記録へ明記し、包んで呼ばないことを申し送る**

いまの記述（「巻き戻りません」）は、**成り立たない範囲を含んでいます。** ここは必ず直してください。

### 2-4【要修正】`created_at` が、その日の最初の発生時刻をマイクロ秒で残します

`src/backend/db/migrate/20260827090000_create_metric_events.rb` 18 行目 `t.timestamps`

移行ファイルの見出し・PR 本文・セキュリティレビュー記録は、そろって「**残すのは軸の名前・クォータ日・件数だけです**」と書いています。**実際には、もう 2 列あります。**

実測しました。

```
{"id"=>47, "axis"=>"quota_exhausted", "count"=>2, "occurred_on"=>2026-08-27,
 "created_at"=>2026-08-26 17:10:35.925698 UTC, "updated_at"=>2026-08-26 17:10:35.925698 UTC}
```

問題は 2 つあります。

**(a) 再識別の手がかりになります。** `created_at` は、その日にはじめて上限に達した瞬間のマイクロ秒です。`quota_consumptions`（`user_id` を持ちます）・`prompt_requests`・アプリケーションログのいずれとも時刻で突き合わせられますので、**「その日の最初に上限へ達したのがどなたか」が絞り込めます。** 件数が小さい日（B2B の初期はほぼそうなります）はなおさらです。CC（個人に関わる情報を最小限にすること）と、Issue #63 の受け入れ条件「個人を特定できる形で記録しません」に対する留保です。

**(b) テストがこの点を検めていません。** `src/backend/spec/services/metrics/recorder_spec.rb` 45-50 行

```ruby
columns = MetricEvent.column_names - %w[id created_at updated_at]
expect(columns).to contain_exactly('axis', 'occurred_on', 'count')
```

**懸念のある 2 列を引いてから検めています。** これでは、`created_at` を足しても引いても結果が変わりません。TM（テストは、壊れたときに赤くなること）に反します。

なお `on_duplicate: Arel.sql('count = metric_events.count + 1')` は `updated_at` に触れませんので、**`updated_at` は 1 件目の時刻のまま止まります。** 「最後に更新した時刻」を意味しない列が残ります。デバッグトレースの観点でも誤解を招きます。

**求めること**：`created_at` ・ `updated_at` を残すのであれば、**残す理由と、それでも個人を特定できないと判断した根拠**を書いてください。残さない、あるいは日単位へ丸めるのであれば、そのようにしてください。いずれの場合も、**PR 本文・移行ファイル・セキュリティレビュー記録の「3 つだけ」という記述を実際に合わせてください。** テストは、引き算をせずに「保存されている列の全体」を検める形へ直してください。
