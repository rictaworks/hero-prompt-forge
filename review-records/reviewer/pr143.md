## 2. 一意索引の違反の包み直し（要件 2）：未達です【要修正】

`reclaim!` が、**`dangling_reservation` を、中断状態のトランザクションの中で呼びます。**

`claim!` は `consumption.with_lock` でトランザクションを開きます。その中で `transition_to!` が一意索引に当たると、PostgreSQL 側でトランザクション全体が中断します。`reclaim!` の `rescue` は、その中断したままの接続で `QuotaConsumption.find_by` を投げます。

```
expected Quota::Reservation::DanglingReservationError,
got #<ActiveRecord::StatementInvalid:
  "PG::InFailedSqlTransaction: ERROR:  current transaction is aborted, ...">
```

**時刻を戻さずに再現できます。**

1. 1 日目：`reserve!(user, 生成リクエストA)`。決着を呼ばずに残します
2. 2 日目：`reserve!(user, 生成リクエストB)`
3. 2 日目：B が失敗し、`settle!(B)` で 2 日目の枠が返還済みになります
4. 2 日目：同じ日の作り直しとして `reserve!(user, 生成リクエストA)` を呼びます

`requirements.md` 4.4 の「失敗したら当日中に作り直せます」は、まさにこの手順です。issue #55 の API がこの形を踏むと、**自前の例外だけを捕まえる作りでは 500 になります。**

## 3. 保存点の使い方（要件 4）：`create!` は妥当です【一部要修正】

`requires_new: true` は妥当です。別接続でコミット前の同一 `(user_id, quota_day)` を作らせ、呼び出し側を包んで実行したところ `ExhaustedError` になります。保存点を外すと `PG::InFailedSqlTransaction` になります。未達は「2」と同じで、`claim!` / `reclaim!` 側に保存点が無い点です。

## 4. 上限到達の読み替えのテスト（要件 5）：達成です【提案】
